01 / 프로젝트

팀에서 자주 하는 일을 하나의 흐름으로

고객 문의를 예로 들면, AI 모델이 티켓의 성격을 판단한 뒤 승인 필요 여부에 따라 답변 초안을 쓰거나 승인 요청을 보냅니다. Nodease에서는 이런 흐름을 자연어로 만들거나 화면에서 노드를 연결해 편집하고 실행할 수 있습니다.

이 흐름에서 사내 자료를 쓰려면 답변할 때마다 사용자가 읽을 수 있는 문서를 골라야 합니다. 제가 맡은 문서 검색 기능은 관련 대목을 찾아 AI에 건네줍니다. 이 방식을 검색 증강 생성(RAG)이라고 합니다. 검색할 문서는 지식베이스 단위로 묶고, 각 문서에서 지금 검색에 쓸 버전을 관리했습니다.

  • FastAPI
  • SQLAlchemy
  • Celery
  • Redis
  • PostgreSQL
  • pgvector
  • pytest
02 / 데이터 처리

새 버전이 준비된 뒤 검색 자료를 교체

문서를 다시 처리할 때 기존 자료를 먼저 지우면, 새 처리가 실패한 동안 검색할 자료도 잃을 수 있습니다. 업로드 요청을 받는 단계와 새 버전을 검색에 반영하는 단계를 나눴습니다.

늦게 도착한 이전 작업의 결과 차단

새 작업이 시작된 뒤 이전 작업의 결과가 늦게 도착할 수 있습니다. 문서 버전과 지식베이스를 잠근 뒤, 상태와 작업 식별값을 확인해 현재 작업의 결과만 반영했습니다. 검색에 쓸 문서 조각인 청크가 없는 버전도 반영을 중단합니다.

version = self._lock_document_version(document_version.id)
kb = self._lock_knowledge_base(version.knowledge_base_id)
self._verify_fencing_token(version, expected_fencing_token)

chunk_count = self._version_chunk_count(version.id)
if chunk_count <= 0:
    raise KnowledgeIngestionFinalizationError("version_has_no_chunks")

# 검사를 통과한 새 버전을 검색에 반영
version.status = "ready"
kb.active_document_version_id = version.id

KnowledgeIngestionFinalizer에서 핵심 부분만 발췌했습니다. 전체 검증과 정리 작업은 아래 고정 코드 링크에서 확인할 수 있습니다.

03 / 검색 실행

검색은 동시에 실행하고, 결과는 요청 순서대로

서로 독립된 지식베이스를 하나씩 조회하면 검색마다 대기시간이 쌓입니다. 권한 검증을 통과한 검색을 최대 5개까지 동시에 실행하도록 바꿨습니다.

검색마다 읽기 전용 DB 세션을 따로 열었습니다. 결과는 완료 순서가 아니라 원래 조회 대상의 순서로 모아, 기존 출처와 인용의 정렬 규칙을 유지했습니다.

지식베이스 10개 조회의 중앙값

순차 처리203.3ms
동시 처리42.4ms
합성 지연을 둔 로컬 검색 비교
지식베이스 수순차 처리 중앙값동시 처리 중앙값
1개20.3ms21.0ms
2개40.7ms21.1ms
4개81.5ms21.4ms
10개203.3ms42.4ms

PR #632의 과거 시험 기록입니다. 지식베이스마다 20ms의 합성 지연을 두고 로컬에서 20회 반복했습니다. 실제 DB, 임베딩 모델, 네트워크를 포함한 서비스 응답시간은 아닙니다. 1개 조회에서는 오히려 소폭 느려졌습니다.

동시 검색에서 함께 확인한 항목

  • 한 번에 실행하는 검색 수를 제한했습니다.
  • 사용자의 조직과 허용된 지식베이스 범위에서 조회하고, 검색별 DB 세션을 분리했습니다.
  • 시간 초과와 취소에 따른 세션 정리를 처리하고, 오류 원문 대신 정해진 오류를 전달했습니다.
04 / 비교 실험

검색 방식과 평가 자료를 함께 점검

계층형 검색을 먼저 적용한 뒤, 문서의 계층을 구분하지 않는 평면형 검색과 비교했습니다. 같은 원문과 청크, 임베딩, 권한, 상위 5개 조건을 맞춘 100문항 개발 실험에서 개선 폭은 작았습니다.

정답 근거 보정 전 검색 지표
지표평면형계층형
Recall@543.89%45.00%
Hit@548.89%50.00%
MRR@529.80%30.02%

상위 5개 결과에서 Recall@5는 필요한 근거를 얼마나 찾았는지, Hit@5는 정답 근거를 하나라도 찾았는지, MRR@5는 첫 정답 근거가 얼마나 앞에 나오는지를 나타냅니다.

평가에 쓴 정답 근거도 다시 확인했습니다

후속 AI 검토에서 31문항의 정답 근거를 수정해야 한다는 결과가 나왔습니다. 위 지표는 수정 전 평가 자료로 계산한 값입니다. 사람이 정답 근거를 검토하고, 수정한 평가 자료를 고정해 다시 비교하는 작업이 남아 있습니다.
