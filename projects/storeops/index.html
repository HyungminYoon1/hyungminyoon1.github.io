01 / 프로젝트

매장 담당자가 마지막 결정을 내리도록

재고가 적은 상품을 알려주는 일과 그 상품을 주문할 초안을 만드는 일에는 차이가 있습니다. 조회한 내용은 바로 보여주고, 새 기록을 만드는 제안은 담당자가 상품과 수량을 확인한 뒤 승인하도록 했습니다.

재고와 사용자, 매출은 모두 시험용으로 구성했습니다. 승인을 거친 결과도 합성 매장에 저장되는 초안입니다. 같은 제안이 두 번 들어왔을 때와 실행 도중 응답을 잃었을 때를 따로 살펴봤습니다.

  • Java
  • Spring Boot
  • MCP
  • PostgreSQL
  • 행 수준 보안
  • React
02 / 승인과 권한

승인 시점에 권한과 제안 상태를 다시 확인

제안을 만든 뒤 사용자의 권한이 바뀌거나 다른 요청이 먼저 처리될 수 있습니다. 승인 서비스에서 현재 매장 권한, 제안 버전, 만료 시간과 실행 인자를 다시 확인했습니다.

승인 시점의 검사 항목
검사막으려는 상황
현재 사용자와 매장 권한권한이 없는 사용자의 승인 또는 다른 매장 접근
제안 상태와 기대 버전이미 처리되거나 변경된 제안을 새 요청처럼 실행
만료 시간과 실행 인자 해시기한이 지났거나 승인 대상과 인자가 다른 실행
동일 요청 식별값같은 승인 요청의 재전송으로 새 실행 생성

승인 판단과 요청 처리, DB 연결을 분리

승인과 실행 상태를 결정하는 로직은 Java 서비스에 두고, HTTP 요청 처리와 DB 연결은 별도 계층으로 나눴습니다. 조직과 매장 범위를 검사하고, DB의 행 수준 보안으로도 데이터 접근을 제한했습니다.

MCP에는 매출 요약, 재고 위험 조회, 재주문 초안 생성 도구를 연결했습니다. 호출 전에 도구 이름과 인자 형식, 허용된 동작을 확인했습니다.

03 / 실패 처리

결과 미확인 시 재실행 차단

도구가 작업을 마친 뒤 응답만 유실될 수 있습니다. 이를 확정 실패로 판단하고 다시 실행하면 초안이 중복될 수 있어, 성공과 확정 실패 외에 결과 미확인 상태를 따로 뒀습니다.

같은 승인 요청을 다시 보냈을 때

요청 식별값으로 기존 처리 상태를 확인합니다. 재전송을 새 도구 실행으로 처리하지 않습니다.

try {
    result = gateway.invoke(command);
} catch (ToolPolicyException policyFailure) {
    result = new ToolInvocationResult(
        FAILED, policyFailure.code(), null);
} catch (RuntimeException unexpectedFailure) {
    result = new ToolInvocationResult(
        OUTCOME_UNKNOWN, "TOOL_OUTCOME_UNKNOWN", null);
}

승인 서비스의 예외 처리를 축약했습니다. 정책 위반과 예상치 못한 오류를 서로 다른 실행 상태로 기록합니다.

04 / 검증

동시 요청과 응답 유실을 나누어 시험

2026년 8월 20일 합성 도구 검증 기록
시험 상황당시 확인한 결과
같은 키의 동시 요청 32개합성 도구의 초안 등록 1건
같은 키와 다른 실행 인자요청 충돌로 거부
호출 뒤 결과를 알 수 없음호출 1회, 자동 재시도 0회
허용된 도구 정보와 서버 정보 불일치도구 호출 0회
서명된 요청의 필수 정보 불일치도구 동작 전에 거부

2026.08.20 Phase 5 검증 보고서에 기록한 결과입니다. 32개 동시 요청은 단일 프로세스의 인메모리 합성 도구로 시험했습니다. 여러 서버와 실제 외부 발주 연동 환경의 중복 방지는 추가 검증 과제로 남아 있습니다.

DB 저장 규칙과 MCP 연결도 확인

격리된 PostgreSQL에서 제안과 실행 이력을 저장하는 테이블의 제약조건, 중복 식별값과 행 수준 보안을 확인했습니다. MCP 연결은 시험마다 생성한 키를 사용해 같은 PC의 클라이언트와 서버 사이에서 확인했습니다. 운영 환경과 분리한 시험입니다.
